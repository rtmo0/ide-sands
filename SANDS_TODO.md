# Sands — план работ

IDE на основе Zed, в которой проект целиком живёт в Docker Sandbox: несколько репозиториев, агенты
(Claude CLI, Codex и т. п.), тулчейны, отладчики и подключённый контекст — базы данных, Kubernetes, S3,
LDAP и прочее. На хосте — только Sands и `sbx`. Нормальная разработка с отладкой для C++, Rust, Go,
Flutter/Dart, Python, Node.js, веба (Vue и т. п.) и C#.

## Принятые решения

- **Форк Zed с полной переработкой интерфейса.** Оркестрация через песочницы встроена в IDE: проект =
  песочница; агенты, сервисы, контекст и сетевая политика управляются из интерфейса.
- **У каждого проекта свой набор агентов** (Claude Code, Codex, Gemini, OpenCode и т. п.) — подключаются
  и отключаются в проекте.
- **Контекст проекта — плагины.** Базы данных, Kubernetes, S3, LDAP и всё остальное подключаются как
  плагины: плагин приносит в песочницу инструменты, переменные, конфиги, сетевые правила, учётные данные
  и MCP-сервер для агентов, а в IDE — свою панель.
- **Изоляция — Docker Sandboxes (`sbx`)**: microVM на проект, свой Docker Engine внутри, сеть закрыта по
  умолчанию, секреты на хосте подставляет прокси.
- **Подключение к песочнице:** на старте штатный SSH-транспорт Zed (`sbx setup ssh` → хосты `<имя>.sbx`),
  целевой вариант — нативный транспорт `sbx exec`.
- **Апстрим:** регулярно вливаем zed-industries/zed. Новое — в отдельных крейтах, правки существующих
  крейтов минимальны; общеполезное (sbx-транспорт, отладчик C#) предлагаем в апстрим.
- **Отказались:** форк Orca (нет отладчика и LSP, 33 тыс. файлов на поддержку), VS Code (неудобен,
  Remote-SSH проприетарный).
- **Лицензия:** форк остаётся под GPL-3.0 (`gpui` — Apache-2.0).

## Архитектура

```
Sands (форк Zed) на хосте
  ├─ crates/sbx                клиент sbx: create/ls/exec/cp/ports/policy/secret/template, JSON, версия
  │                            (имя `sandbox` занято апстримом — изоляция процессов агента)
  ├─ crates/sandbox_project    манифест проекта (sands.yaml → sbxenv.yaml), провижн: репозитории,
  │                            kits, сервисы, агенты, плагины контекста, секреты, политика
  ├─ crates/context_plugins    загрузка плагинов, схема настроек, провижн в песочницу, проверки,
  │                            стратегии учётных данных, хост-релеи
  ├─ crates/sandbox_ui         панели: проекты и песочницы, агенты, порты, сервисы, сеть и одобрения,
  │                            панели плагинов (Kubernetes, базы данных, S3, LDAP…)
  ├─ crates/remote/src/transport/sbx.rs   нативный транспорт (после SSH-этапа)
  └─ переработанный интерфейс (workspace, title_bar, sidebar, recent_projects, agent_ui)

Песочница (microVM): remote_server (файлы, LSP, git, терминалы, DAP, ACP-агенты),
                     инструменты и MCP-серверы плагинов, сервисы в своём Docker
```

### Плагин контекста

Плагин описывает манифест; динамику (обнаружение ресурсов, панель) — код. Что объявляет плагин:

| Часть | Пример для Postgres | Пример для Kubernetes |
|---|---|---|
| Настройки (схема) | хост, порт, база, пользователь | кластер, контекст, namespace |
| Инструменты в песочнице (kit) | psql, pgcli | kubectl, helm, k9s |
| Переменные окружения | `DATABASE_URL` | `KUBECONFIG` |
| Файлы конфигурации | `~/.pgpass` (если нужен) | kubeconfig с токеном-заглушкой |
| Сетевые правила | `db.internal:5432` | `api.cluster:6443` |
| Стратегия учётных данных | хост-релей | подстановка в заголовок прокси |
| MCP-сервер для агентов | запросы, схема | ресурсы, логи, события |
| Панель в IDE | подключения, запросы, таблицы | ресурсы, логи, port-forward |
| Проверка | `SELECT 1` | `kubectl auth can-i` |

Стратегии учётных данных — секрет по возможности не попадает в песочницу:

- **Подстановка в заголовок** (`sbx secret set-custom`): HTTP(S) с токеном — Kubernetes (bearer), HTTP API,
  реестры.
- **Хост-релей:** протоколы не на HTTP (Postgres, MySQL, Redis, LDAP bind) — релей на хосте держит пароль и
  сам аутентифицируется, песочница подключается к релею без секрета.
- **Краткоживущие учётные данные внутри:** где запрос подписывается секретом (S3 SigV4) — STS-токены с
  минимальными правами и коротким сроком либо подписывающий релей на хосте.
- **Внутри песочницы как есть:** только по явному выбору пользователя, с предупреждением в интерфейсе.

Опорные места в коде Zed:

- SSH-транспорт, системный `ssh` с ControlMaster: `crates/remote/src/transport/ssh.rs`
  (`upload_binary_over_ssh` — строка ~155).
- Docker-транспорт как образец для `sbx`: `crates/remote/src/transport/docker.rs`; проброс портов там не
  реализован (`_port_forward` в `build_command`).
- Трейт подключения: `RemoteConnection` в `crates/remote/src/remote_client.rs` (~1477); варианты
  `RemoteConnectionOptions` (~1361) используются в 15 местах в 9 крейтах.
- ACP-агенты в удалённом проекте стартуют через `build_stdio_command`:
  `crates/agent_servers/src/acp/transport.rs` (~43); команду выдаёт удалённая сторона
  (`crates/project/src/agent_server_store.rs`, `RemoteExternalAgentServer`).
- Отладка в удалённом проекте и проброс TCP-порта адаптера: `crates/project/src/debugger/dap_store.rs`
  (~308). TCP нужен Delve, debugpy, js-debug; CodeLLDB и GDB работают через stdio.
- Worktree для параллельных тредов в удалённых проектах: `crates/git_ui_core/src/worktree_service.rs`
  (~789).
- API расширений (WASM: DAP, MCP, без UI): `crates/extension_api/src/extension_api.rs`, `wit/` — основа
  для API плагинов контекста.

### Итоги этапа 0 (2026-11-03, sbx 0.50.1, macOS 27.2, Apple Silicon)

Подтвердилось:

- Песочница — Ubuntu 26.04 **aarch64**, 14 vCPU, 11 ГБ RAM, 20 ГБ диска, свой Docker 29.9, `sudo` без
  пароля; go, node, python предустановлены.
- `sbx setup ssh` даёт `*.sbx` через `ProxyCommand sbx ssh proxy`, без ключей. Сгенерированный конфиг
  ставит `ControlMaster no`, но Zed подключается (его собственные `-o ControlMaster` в командной строке
  имеют приоритет). Проброс портов `ssh -L` работает.
- Внутри: `HTTP(S)_PROXY=gateway.docker.internal:3128`, CA прокси в системном хранилище, ключи агентов
  (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GH_TOKEN` и др.) — заглушки, которые подставляет прокси.
- Хост доступен как `host.docker.internal` — хост-релеи возможны.
- Отладочная сборка форка сама кросс-собирает remote server (`cargo zigbuild`, aarch64-musl) и закачивает
  его; на хосте нужны `zig` и `cargo-zigbuild`.

Меняет план:

- **Сеть по умолчанию открыта.** Локальная политика — `default-allow-all`, а не «закрыто по умолчанию».
  Sands должен сам выставлять политику (`sbx policy init` / deny-правила) при создании проекта, а
  проверку хост-релея повторить при закрытой политике.
- **lldb не работает в microVM.** `lldb-server` (LLDB 21 из Ubuntu и встроенный в CodeLLDB) падает при
  запуске процесса (`Sending vRun packet failed`); gdb на том же ядре работает. Для Rust/C++ пока GDB;
  CodeLLDB — дефолт Zed для Rust, поэтому причину нужно выяснить (вероятно, регистры aarch64 в VM) и
  сообщить Docker/LLVM.
- **Доверие к worktree.** LSP в удалённом проекте ждут доверия (Restricted Mode). Для Sands граница
  доверия — песочница: проекты-песочницы стоит доверять автоматически, не включая
  `trust_all_worktrees` глобально.
- Загрузки LSP через прокси иногда обрываются (ruff с GitHub, eslint из npm) — нужны повторы или
  предустановка в kits.
- Remote server релизных сборок форка нельзя качать с zed.dev (версии не совпадут) — нужно публиковать
  свои артефакты (CI уже собирает их) и научить `auto_update` брать их из релизов форка.

## Известные ограничения

- Прокси `sbx` подставляет секреты только в заголовки HTTP(S); для остальных протоколов нужны хост-релеи
  или учётные данные внутри песочницы.
- Flutter: iOS-сборка невозможна (нужен macOS); Android-эмулятор внутри microVM, вероятно, не заработает —
  Flutter Web или устройство через `adb connect`.
- C#: WPF/WinForms не работают; .NET/ASP.NET работают.
- GUI-приложения: дисплея нет, только web через проброс портов.
- Фронтенд в браузере отлаживается DevTools браузера.
- Kubernetes с клиентскими сертификатами: подстановка невозможна — релей или ServiceAccount с
  минимальными правами внутри.
- `sbx` — закрытый продукт Docker; CLI уже менялся (`docker sandbox` → `sbx`). Фиксировать версию,
  держать зависимость в крейте `sbx`.
- Глубокая переработка интерфейса удорожает слияния с апстримом — главный риск поддержки форка.
