# Sands — архитектура проекта, агентов и безопасности

Черновик дизайна (2026-11-13). Дополняет `SANDS_TODO.md` (план работ) и `SANDS_DESIGN_PLAN.md`
(внешний вид). Здесь — модель проекта, граница доверия, агентский harness с дорогими и дешёвыми
моделями, скиллы, MCP, сеть, секреты и экраны, которые всем этим управляют.

## 1. Принципы

- **Один проект — одна песочница.** В проекте несколько репозиториев, несколько агентов, свои
  скиллы, MCP-серверы, плагины контекста и сеть. Всё, что исполняет код, живёт в песочнице
  проекта.
- **Граница доверия — между хостом и песочницей.** Хост держит то, что решает пользователь:
  конфигурацию проекта, политику, секреты, ключи моделей, одобрения. Песочница — всё,
  что могут потрогать агент, репозиторий и зависимости.
- **Содержимое песочницы для хоста — данные, а не конфигурация.** Хост не исполняет и не
  применяет как настройки то, что лежит в песочнице, без явного одобрения пользователя.
- **Внутри песочницы агент всемогущ.** У пользователя `agent` там `sudo` без пароля (этап 0),
  поэтому любые «только для чтения» файлы внутри — удобство, а не защита. Жёсткие гарантии даёт
  только хост: что запускается на хосте, куда пускает прокси, какие ключи и модели доступны.
- **Дорогие модели — для планирования, дешёвые — для работы.** Это правило исполняет harness
  (инструменты и модели ролей), а не просьба в промпте.

## 2. Модель угроз

Кого опасаемся: агента, которого перехватила инъекция промпта (из репозитория, веб-страницы,
ответа MCP, issue); вредоносного репозитория или зависимости; вредоносного или скомпрометированного
MCP-сервера или скилла.

Инварианты — каждый проверяется тестом:

| # | Инвариант | Где обеспечивается |
|---|---|---|
| I1 | Ничто из песочницы не исполняется на хосте | `context_server_store`, загрузка скиллов, задачи, хуки git |
| I2 | Файлы песочницы не становятся настройками хоста без одобрения | `project_settings`, `agent_skills`, одобренный снимок `.sands/` |
| I3 | Секреты не попадают в песочницу открытым текстом (кроме явного выбора) | прокси `sbx`, хост-релеи, шлюз моделей |
| I4 | Исходящая сеть закрыта по умолчанию, у каждого правила есть источник | политика `sbx` |
| I5 | Конфигурацию проекта меняет только пользователь через интерфейс Sands | `sands_project` |
| I6 | Дорогая модель (уровень `plan`) доступна только ролям, которым она назначена | harness, шлюз моделей |
| I7 | Изменения агента попадают на хост только через проверку | ревью перед fetch/merge/push |
| I8 | Проекты не видят друг друга: свои песочницы, релеи, секреты | `sbx`, релеи привязаны к песочнице |

### Найдено при анализе: I1 и I2 сейчас нарушены

`.zed/settings.json` внутри песочницы может запустить процесс **на хосте**:

1. Sands автоматически доверяет worktree песочниц
   (`crates/sandbox_ui/src/sandbox_ui.rs`, `trust_sandbox_worktrees`).
2. Доверенный worktree применяет свои локальные настройки
   (`crates/project/src/project_settings.rs`, `update_settings`).
3. В настройках проекта есть `context_servers`
   (`crates/settings_content/src/project.rs`), их собирают со всех worktree
   (`crates/project/src/context_server_store.rs`, `resolve_all_context_server_settings`).
4. У сервера по умолчанию `remote: false`, и в удалённом проекте такой сервер запускается
   локальным процессом на хосте (`create_context_server`). HTTP-серверы всегда вызываются с хоста.

Итог: агент пишет в `.zed/settings.json` `context_servers` с произвольной командой → Sands
запускает её на хосте с правами пользователя. Для HTTP — запросы с хоста по адресу из песочницы
(доступ к localhost хоста). Вывод сделан по коду, вживую не воспроизведён — первым делом нужен
тест-эксплойт, затем исправление (раздел 7).

## 3. Компоненты

```
Хост (Sands)                                             Песочница проекта (microVM)
┌─────────────────────────────────────────────┐          ┌───────────────────────────────────┐
│ sandbox_ui: проекты, чат, настройки, сеть,  │          │ /workspace/<repo>…   репозитории  │
│             одобрения, аудит                │          │ remote_server: файлы, LSP, DAP,   │
│ sands_project: модель, хранилище,           │   SSH /  │   терминалы, git, задачи          │
│   реконсилятор, материализация конфигов ────┼─ sbx ──▶ │ ~/.sands/ (сгенерировано):        │
│ agent (Sands Agent): оркестратор, роли,     │   exec   │   skills/, agents/, mcp.json      │
│   уровни моделей ───────────────────────────┼─────────▶│ внешние агенты: claude, codex…    │
│ context_server_store: MCP только remote ────┼─────────▶│ MCP-серверы (stdio)               │
│ sbx: create/policy/secret/ports/exec        │          │ сервисы в своём Docker            │
│ брокер секретов: sbx secret, хост-релеи     │◀─────────┤ прокси sbx: сеть по политике,     │
│ шлюз моделей: ключи, модели, журнал         │◀─────────┤   подстановка секретов            │
│ аудит: проект/audit.jsonl                   │          └───────────────────────────────────┘
└─────────────────────────────────────────────┘
```

Встроенный Sands Agent работает на хосте: держит цикл модели и ключи, а инструменты (файлы,
терминал, MCP) исполняет через удалённый проект в песочнице. Внешние агенты (Claude Code, Codex,
Gemini, OpenCode) работают целиком в песочнице, с чатом Sands их связывает ACP.

## 4. Модель проекта (`crates/sands_project`)

Новый крейт — модель, хранилище, реконсилятор и генерация конфигов агентов. Заменяет
`project_connections.json` и императивное создание в `new_project_modal.rs`.

Описание проекта — `.sands/project.yaml` в основном репозитории (см. ниже). На хосте:
`<data_dir>/projects/<project-id>/` — `approved.json` (одобренный снимок `.sands/` каждого
репозитория: хеш и текст файлов), дальше — ссылки на секреты, `audit.jsonl`, `usage.jsonl`.

```rust
struct Project {
    id: ProjectId,
    name: String,                       // имя песочницы
    sandbox: SandboxSpec,               // cpus, memory, ports, template
    repositories: Vec<Repository>,
    network: NetworkPolicy,
    models: ModelTiers,
    agents: Vec<AgentSpec>,
    skills: Vec<SkillRef>,
    mcp_servers: Vec<McpServerSpec>,
    plugins: Vec<PluginInstance>,       // Kubernetes, Postgres… (приносят MCP, скиллы, сеть, секреты)
    secrets: Vec<SecretRef>,            // только ссылки; значения — в связке ключей хоста / sbx
}

struct Repository {
    id: RepositoryId,
    source: RepositorySource,           // Local { path, mode: Clone | ReadOnly } | Git { url, branch }
    directory: String,                  // путь в песочнице
    primary: bool,
}

struct NetworkPolicy {
    mode: NetworkMode,                  // DenyAll по умолчанию
    rules: Vec<NetworkRule>,            // host:port + origin
}
enum RuleOrigin { User, Agent(AgentId), Plugin(PluginId), McpServer(McpServerId), Toolchain(Toolchain) }

struct ModelTiers { plan: ModelRef, work: ModelRef, fast: ModelRef }
enum Tier { Plan, Work, Fast }

struct AgentSpec {
    id: AgentId,                        // "planner", "worker", "claude-code"…
    kind: AgentKind,                    // Native | External(ExternalRuntime)
    tier: Tier,
    tools: ToolSet,                     // read, search, edit, terminal, spawn, mcp:<id>/<tool>…
    skills: Vec<SkillId>,
    mcp_servers: Vec<McpServerId>,
    may_spawn: Vec<AgentId>,
    instructions: Option<String>,
}

struct McpServerSpec {
    id: McpServerId,
    transport: McpTransport,            // Stdio { command, args, env } | Http { url } — оба в песочнице
    secrets: Vec<SecretRef>,
    network: Vec<NetworkRule>,
    tool_approval: ToolApproval,        // Always | Never | ForTools(Vec<String>)
}

```

Скиллы, агенты и MCP есть ещё и глобально (для всех проектов) — в проект они добавляются ссылкой.

### Каталог `.sands/` — единственный формат проекта

Вся конфигурация проекта в репозитории живёт в `.sands/`. Sands не читает `.zed/`, `.vscode/`,
`.agents/`, `.claude/`, `.mcp.json` — их содержимое переносится миграцией (ниже).

```
.sands/
  project.yaml      агенты и роли, уровни моделей (без ключей), тулчейны, сервисы,
                    плагины, правила сети
  settings.json     настройки редактора (схема прежняя, из .zed/settings.json), без context_servers
  tasks.json        задачи (формат Zed; из .vscode/tasks.json конвертируется)
  debug.json        конфигурации отладки (из .vscode/launch.json и .zed/debug.json)
  mcp.json          MCP-серверы проекта (stdio в песочнице, HTTP через мост)
  agents/<роль>.md  роли: frontmatter (tier, tools, skills, mcp, may_spawn) + инструкции
  skills/<имя>/     скиллы по спецификации Agent Skills (SKILL.md, scripts/, references/)
  instructions.md   общие инструкции для всех агентов проекта (аналог AGENTS.md / CLAUDE.md)
```

Секретов в `.sands/` нет никогда — только имена (`secret: github`), значения на хосте.

В проекте с несколькими репозиториями проектный `.sands/` лежит в основном репозитории; у
остальных репозиториев свой `.sands/` может содержать только `tasks.json`, `debug.json` и
`skills/` — они относятся к своему репозиторию и сливаются с проектными.

### `.sands/` — предложение, а не приказ

`.sands/` лежит в песочнице, и агент может его переписать. Поэтому действует не файл, а
**одобренный снимок** на хосте (`<data_dir>/projects/<id>/approved/`, с хешем каждого файла):

- Безопасные для хоста части (`settings.json` без исполняемых полей, `tasks.json`, `debug.json` —
  они исполняются в песочнице) применяются сразу.
- Части, которые расширяют права, требуют одобрения: роли и их инструменты, уровни моделей и
  MCP, скиллы, правила сети, плагины, `instructions.md`. Изменение такого файла (агентом,
  коммитом, `git pull`) показывается полосой «`.sands/` изменён: 3 изменения» с диффом и кнопками
  «Принять / Отклонить». До решения действует прежний снимок.
- Изменения из интерфейса Sands пишутся в `.sands/` и сразу попадают в снимок — их можно
  закоммитить и раздать команде.

### Миграция из VS Code, Zed и агентов

При создании или открытии проекта Sands ищет чужие настройки и предлагает перенести их одним
экраном со списком «что → куда» и превью итоговых файлов:

| Найдено | Куда | Как |
|---|---|---|
| `.zed/settings.json` | `.sands/settings.json` | 1:1, кроме `context_servers` → `.sands/mcp.json` |
| `.zed/tasks.json`, `.vscode/tasks.json` | `.sands/tasks.json` | конвертер VS Code (`dependsOn`, `inputs`, переменные) уже есть в `crates/task` |
| `.zed/debug.json`, `.vscode/launch.json` | `.sands/debug.json` | конвертер `launch.json` (`preLaunchTask`, типы отладчиков) уже есть |
| `.vscode/settings.json` | `.sands/settings.json` | только то, что имеет аналог (отступы, форматирование, файлы) |
| `.vscode/mcp.json`, `.mcp.json`, `context_servers` | `.sands/mcp.json` | с пометкой «будет работать в песочнице» |
| `.agents/skills/`, `.claude/skills/` | `.sands/skills/` | копирование |
| `.claude/agents/*.md` | `.sands/agents/` | поле `model` → `tier` |
| `AGENTS.md`, `CLAUDE.md` | `.sands/instructions.md` | предложение ссылки или копии |

- Исходные файлы не удаляются и не меняются; Sands их просто больше не читает. Удаление — отдельная
  галочка, по умолчанию выключена (ими могут пользоваться коллеги без Sands).
- Всё, что переносится в части с одобрением (MCP, скиллы, роли), сразу попадает в предложение — то
  есть миграция не обходит проверку.
- Отклонённую миграцию Sands больше не предлагает, пока не изменятся исходные файлы; вручную —
  команда `sands: migrate project settings`.

### Реконсилятор

Желаемое состояние (`Project`) → проверка фактического (`sbx ls`, `policy`, `probe`, файлы в
песочнице) → список шагов: создать песочницу, применить политику, клонировать репозитории,
поставить тулчейны и агентов, зарегистрировать секреты, сгенерировать конфиги агентов, поднять
MCP. Каждый шаг идемпотентен и виден в интерфейсе как строка с состоянием. Так же проходит
повторное открытие проекта: расхождение (например, агент переписал свой конфиг в `~/.sands`)
показывается и исправляется перегенерацией.

## 5. Агентский harness

### Уровни и роли

Проект сопоставляет уровни с моделями (`plan` → дорогая, `work` → рабочая, `fast` → дешёвая).
Роли ссылаются на уровень, поэтому сменить модель можно в одном месте.

| Роль | Уровень | Инструменты | Назначение |
|---|---|---|---|
| planner | plan | чтение, поиск, `spawn_agent`, вопрос пользователю | разбирает задачу, пишет план, раздаёт шаги, перепланирует |
| worker | work | чтение, правка, терминал в своём worktree, MCP проекта | выполняет шаг плана |
| explorer | fast | чтение, поиск | ищет по коду и документации для планировщика |
| reviewer | work или fast | чтение, дифф, запуск тестов | проверяет шаг по критериям приёмки |
| utility | fast | — | сводки тредов, сжатие контекста, сообщения коммитов |

Роли — это развитие профилей Zed (`AgentProfile`: инструменты + модель). К профилю добавляются
уровень, скиллы, MCP и список ролей, которые он может запускать.

### Поток задачи

```
пользователь ─▶ planner (plan) ─▶ План: шаги, критерии приёмки, файлы каждого шага
                    │                  │ (пользователь может поправить и одобрить)
                    │                  ▼
                    │      ┌──── worker #1 (work, worktree A) ──┐
                    │      ├──── worker #2 (work, worktree B) ──┤ шаги с непересекающимися файлами
                    │      └──── explorer (fast) ───────────────┘ идут параллельно
                    │                  ▼
                    │            reviewer: дифф + тесты
                    │       ок ─▶ следующий шаг / слияние worktree
                    └─◀── не ок N раз ─ перепланирование (а не перевод worker на дорогую модель)
```

### Где это обеспечивается в коде

- Набор инструментов треда собирается из роли (`crates/agent/src/thread.rs`), а не из
  глобального профиля. У planner нет правки и терминала — физически.
- `spawn_agent` принимает `role` вместо `model`. Модель выбирает harness по уровню роли.
  Запуск роли уровня `plan` из `spawn_agent` разрешён только если это есть в `may_spawn`.
  Это заменяет `subagent_model` (`crates/agent_settings/src/agent_settings.rs`).
- `thread_summary_model`, `compaction_model`, `commit_message_model` → уровень `fast` проекта.
- Расход пишется в `usage.jsonl` по роли и проекту (виден в Audit). Жёстких денежных лимитов в
  интерфейсе нет; при необходимости — настройка шлюза моделей.
- План — структурированный результат planner (шаги, критерии, файлы), отображается в чате как
  отдельный блок со статусами шагов, исполнителями и их worktree.

### Внешние агенты

Их харнесс исполняется внутри песочницы, поэтому из конфигурации проекта Sands **генерирует** их
настройки в домашний каталог песочницы (не в репозиторий):

- Claude Code: `~/.claude/settings.json` (модель, разрешения, statusLine уже ставится),
  `~/.claude/agents/<роль>.md` с полем `model` по уровню, `~/.claude/skills/` — одобренные скиллы,
  MCP проекта.
- Codex: `~/.codex/config.toml` — профили с моделью и усилием рассуждения по уровням, `mcp_servers`.
- Gemini, OpenCode — аналогично, по мере поддержки.

Так как агент внутри может переписать эти файлы, для внешних агентов уровни — соглашение, а не
гарантия. Гарантию даёт только **шлюз моделей** на хосте (опция): `ANTHROPIC_BASE_URL` /
`OPENAI_BASE_URL` в песочнице указывают на хост-релей, тот держит ключи, пропускает только
разрешённые проекту модели и пишет журнал. Работает с API-ключами; вход по
подписке (OAuth) — пока без жёстких гарантий.

## 6. Скиллы

Источники: встроенные, глобальные пользователя (`~/.sands/skills` на хосте), проектные
(`.sands/skills/` в репозиториях проекта, после одобрения по хешу).

- `agent_skills` ищет `.sands/skills` вместо `.agents/skills` и для проекта-песочницы загружает
  **одобренный снимок** с хоста, а не живые файлы worktree — их агент может переписать.
- В песочницу одобренные скиллы копируются в `~/.sands/skills/` (для внешних агентов и для
  скриптов скиллов). Скрипты исполняются только в песочнице.
- Скилл может объявить нужные инструменты, MCP и уровень модели (через `metadata`) — при
  подключении к роли Sands показывает, что он добавит.

## 7. MCP

- В проекте-песочнице **все** MCP-серверы работают в песочнице: stdio — через удалённую команду
  (механизм `remote: true` уже есть), HTTP — через мост stdio↔HTTP внутри песочницы, чтобы запросы
  шли через прокси, политику сети и подстановку секретов.
- `context_server_store` в проекте-песочнице берёт серверы только из одобренного
  `.sands/mcp.json` и глобальных серверов Sands, принудительно `remote`. Ключ `context_servers` в
  настройках worktree не читается вовсе (исправление уязвимости из раздела 2).
- Доступ по ролям: агенту видны только серверы из его `mcp_servers`; внешним агентам в конфиг
  попадают только они.
- Одобрение вызовов: для опасных инструментов MCP (запись в базу, `kubectl delete`) — запрос
  пользователю, как у инструментов агента.
- Плагин контекста = MCP-сервер + скиллы + правила сети + стратегия секретов + панель. Первый
  такой плагин — существующий Kubernetes.

## 8. Сеть, секреты, изменения на хост

- Политика собирается слоями: модели выбранных агентов, реестры пакетов тулчейнов, правила
  плагинов и MCP, правила пользователя. У правила есть источник: отключили плагин — ушли его
  правила.
- Живой журнал (`sbx` network log): заблокированный запрос → «Разрешить один раз / всегда /
  Запретить» прямо из интерфейса. Агент не может разрешить себе хост сам.
- Секреты: подстановка в заголовок прокси (HTTP), хост-релей (Postgres, Redis, LDAP), краткоживущие
  учётные данные (S3), «внутри как есть» — только явно, с предупреждением.
- Изменения на хост: перед `git fetch` из `sandbox-<имя>` и перед push — дифф с подсветкой
  рискованных файлов (`.git/hooks`, `.github/`, CI, скрипты `package.json`, Makefile, `.vscode/`,
  `.zed/`, `.sands/`, `.agents/`, `.claude/`). Push — с учётными данными хоста после ревью или через
  секрет прокси, по настройке проекта.

## 9. Git и изменения

Главное — всегда видно, что меняется и где, и исходный код рядом.

- **Git-панель проекта** показывает все репозитории проекта: ветка, изменённые и подготовленные
  файлы, коммиты, расхождение с хостом (сколько коммитов ещё не забрано на хост) и с сервером.
- **Worktree агентов.** У каждого шага плана свой worktree и ветка `sands/<шаг>`. Список worktree
  показывает агента, шаг, дифф против базовой ветки и действия «Открыть дифф», «Слить»,
  «Отбросить». Дифф — многофайловый (project diff Zed) с переходом в исходник, blame и историей
  файла.
- **Чат связан с git.** Каждая правка агента в треде — ссылка на её дифф; блок плана показывает
  изменённые файлы шага и итог `+/−`.
- **Исходный код.** Дерево файлов показывает все репозитории проекта; worktree агента можно
  открыть отдельным корнем, чтобы читать код, пока агент работает.
- **Обмен с хостом.** Локальный репозиторий хоста клонирован в песочницу; изменения забираются
  на хост `git fetch` из `sandbox-<имя>` после проверки (раздел 8), push — через секрет `github`.

Опора в коде: `crates/git_ui` (панель, project diff), `crates/git_ui_core/src/worktree_service.rs`
(worktree в удалённых проектах), `action_log` агента (правки в треде).

## 10. Отладка в песочнице

Отладка уже работает через remote server (этап 0): адаптер и программа — в песочнице, интерфейс —
на хосте. Что делает Sands сверх этого:

- **Адаптеры из kits:** debugpy, Delve, js-debug, GDB (Rust, C/C++ — CodeLLDB в microVM не
  работает), netcoredbg (C#), Dart. Ставятся вместе с тулчейном.
- **Конфигурации** — `.sands/debug.json` (миграция из `.vscode/launch.json`); у `main` и тестов
  зелёная стрелка с вариантами Run и Debug.
- **TCP-адаптеры** (Delve, debugpy, js-debug): порт адаптера пробрасывается через SSH; после
  нативного транспорта — через `sbx ports`.
- **Веб-приложения:** dev-сервер в песочнице, порт публикуется (`sbx ports`) и открывается в
  браузере хоста; фронтенд — js-debug, подключённый к браузеру хоста.
- **Сервисы в docker compose** внутри песочницы: attach к процессу в контейнере (Delve, debugpy)
  с пробросом порта.
- **Проверить вживую:** js-debug и фронтенд (Vue, Angular), Flutter web, netcoredbg на arm64.
- Позже: инструмент отладки для агентов (точки останова, стек, переменные) — по умолчанию выключен.

## 11. Удаление проекта

Projects panel → «Delete project…». Проект и песочница — одно целое, удаляются вместе.

- **Всегда удаляется:** песочница (`sbx rm`) со всем внутри — клоны репозиториев, тулчейны, агенты
  и их конфиги; данные проекта на хосте (одобренный снимок, журналы, связи); секреты и правила
  сети проекта в `sbx`; хост-релеи; remote `sandbox-<имя>` в локальных репозиториях хоста.
- **Сначала проверка несохранённого:** по каждому репозиторию — незакоммиченные изменения и
  коммиты, которых нет ни на хосте, ни на сервере. Кнопка «Забрать на хост» делает fetch в ветки
  `sands/<проект>/…` перед удалением.
- **Опционально — репозитории на хосте:** по галочке на каждую локальную папку репозитория, по
  умолчанию выключены. Папки уходят в Корзину macOS, а не стираются. Подтверждение — ввод имени
  проекта.
- Репозитории на серверах (GitHub и т. п.) Sands не удаляет никогда.

## 13. Порядок работ

1. **Исправить уязвимость MCP (I1, I2).** Тест-эксплойт, затем: в проекте-песочнице игнорировать
   `context_servers` из worktree, все серверы — remote.
2. **Переезд на `.sands/`.** `paths::local_settings_folder_name()` → `.sands` (оттуда же берутся
   `tasks.json` и `debug.json`), `agent_skills` → `.sands/skills`, чтение `.vscode/tasks.json` и
   `launch.json` напрямую убрать; экран миграции из `.zed/`, `.vscode/`, `.agents/`, `.claude/`
   на существующих конвертерах `crates/task`.
3. **`sands_project`: модель, `.sands/project.yaml`, одобренный снимок на хосте.** Перенести
   `project_connections.json`; проекты из `sbx ls` без `.sands/` — импорт с настройками по
   умолчанию.
4. **Реконсилятор** вместо `create_project` в мастере; список шагов в интерфейсе.
5. **Удаление проекта**: проверка несохранённого, «Забрать на хост», опциональное удаление папок
   репозиториев в Корзину.
6. **Уровни и роли во встроенном агенте**: инструменты из роли, `spawn_agent(role)`, служебные
   задачи на `fast`.
7. **Шлюз моделей**: ключи на хосте, разрешённые модели по уровням, журнал вызовов.
8. **План как блок в чате**: шаги, исполнители, worktree на шаг, ревью, перепланирование.
9. **Git проекта**: все репозитории в панели, worktree агентов с диффом и слиянием, правки в чате
   со ссылкой на дифф, расхождение с хостом.
10. **Генерация конфигов внешних агентов** (Claude Code, Codex) и проверка расхождений.
11. **Скиллы**: хранилище проекта, предложения из репозитория, одобрение по хешу.
12. **MCP проекта**: реестр, мост HTTP, доступ по ролям, одобрение вызовов; Kubernetes как плагин.
13. **Сеть**: слои правил с источником, одобрения из журнала.
14. **Отладка в песочнице**: адаптеры в kits, Run/Debug у стрелок, проброс портов через
    `sbx ports`, веб-приложения и compose, проверка js-debug и Flutter web.
15. **Ревью изменений на выходе** из песочницы.

## Решения (2026-11-13)

- **Оркестратор — встроенный Sands Agent.** Claude Code и Codex — самостоятельные агенты чата
  проекта, управляются сгенерированными конфигами.
- **`sudo` без пароля у пользователя `agent` в песочнице убираем** (проверить, позволяет ли `sbx`;
  если нет — свой шаблон песочницы). Тогда `~/.sands` и сгенерированные конфиги агентов
  действительно только для чтения.
- **Шлюз моделей — с первого дня.** Все вызовы моделей из песочницы идут через хост: ключи,
  разрешённые модели и журнал (шаг 7 порядка работ).
- **Деньги — не в центре интерфейса.** Стоимость и бюджеты не показываются в чате, плане и
  статус-баре; расход — в журнале и Audit.
